# Reclaim SQLite space from an offline Durable store

`reclaim-offline-sdk-history.ts` removes one eligible conversation and its directly owned transcript, documents, tasks and submissions from a **new compacted copy**. It supports **`@earendil-works/pi-durable` 1.6.1 and 1.7.0**. It checks the input against the exact unprefixed SQLite schema and migration ledger generated by the installed SDK. It does not open the original in SQLite. [SDK issue #12641](https://github.com/earendil-works/pi/issues/12641) requests an upstream maintenance API.

With installed SDK 1.7.0, the opt-in **Piclaw archived-session profile** additionally requires `--piclaw-chat-jid` and `--piclaw-branch-id`. Both native flags are required together and must exactly identify the archived, non-default root chat branch and its routed conversation ID. This checkout must use its local `@earendil-works/pi-durable` 1.7.0 backend: the command performs no package download or live SDK change, and the Piclaw profile refuses any other locally installed backend version.

Piclaw qualification refuses a mismatched archive tuple, dependent branches, any persisted task that is not terminal, or any submission whose indexed or JSON status is not the same settled value from `done` and `unanswered`. NULL, unknown and mismatched status values are rejected before a writable Harness is opened. It also refuses unsupported host effects and retained cross-references. The qualification is intentionally narrower than a general chat deletion: only a settled direct native message cohort with proven terminal answers is accepted. Each source must be a consumed `message` with no parent source or target operation; its binding, submission, and host message must agree on the branch, conversation, source sequence, and an exact `message-row:<rowid>` or `queued-source:<message id>` payload reference. No steering, rich-content row, unsupported timeline shape, queued follow-up, or active host operation is accepted.

## Prepare and inspect an offline Piclaw copy

Stop the owner and make a fully checkpointed copy using the store owner's backup procedure. Keep that closed `source.sqlite` in a canonical, owned, private (`0700`) directory and give the file mode `0600`. A live database's main file alone is not a backup when its journal mode is WAL: committed pages may still be in `-wal`, and read-only SQLite inspection can still create `-shm`/`-wal` sidecars. Use the owner's completed, quiescent backup, not ad-hoc access to the application store.

Inspect a **separate copy** so no application database is opened for inspection and the WAL sidecar behavior is confined to that disposable copy. Do not run UPDATE, archive, delete, checkpoint, journal-mode, or application commands against the source copy; read it only:

```sh
SOURCE=/workspace/tmp/private-maintenance/source.sqlite
INSPECTION=/workspace/tmp/private-maintenance/inspection.sqlite
cp -- "$SOURCE" "$INSPECTION"
chmod 0600 "$INSPECTION"

sqlite3 -readonly -header -column "$INSPECTION" <<'SQL'
SELECT b.chat_jid,
       b.branch_id,
       MIN(b.conversation_id) AS conversation_id,
       COUNT(DISTINCT b.conversation_id) AS distinct_conversations
FROM chat_branches AS h
JOIN piclaw_durable_bindings_v1 AS b
  ON b.chat_jid = h.chat_jid
 AND b.branch_id = h.branch_id
WHERE h.archived_at IS NOT NULL
  AND h.parent_branch_id IS NULL
  AND h.root_chat_jid = h.chat_jid
GROUP BY b.chat_jid, b.branch_id
HAVING COUNT(DISTINCT b.conversation_id) = 1
ORDER BY b.chat_jid, b.branch_id;
SQL
```

Copy the exact `chat_jid`, `branch_id`, and `conversation_id` from the one intended row. Rows with zero or multiple distinct conversations are deliberately absent. The SDK validation still verifies the routed manifest and exact tuple during reclamation.

## Run reclamation on a standalone SDK copy

The output must be a new sibling filename. Compute the digest after the source is fully closed and has no sidecars, then set the approved value in the placeholder variable. This complete Piclaw invocation is copy/paste-ready once the four target/path variables are replaced:

```sh
SOURCE=/workspace/tmp/private-maintenance/source.sqlite
OUTPUT=/workspace/tmp/private-maintenance/reclaimed.sqlite
CHAT_JID='<exact-chat-jid-from-the-query>'
BRANCH_ID='<exact-branch-id-from-the-query>'
CONVERSATION_ID='<exact-conversation-id-from-the-query>'
EXPECTED_SOURCE_SHA256='<approved-lowercase-sha256-from-sha256sum>'

sha256sum "$SOURCE"
bun runtime/scripts/reclaim-offline-sdk-history.ts \
  --source "$SOURCE" \
  --output "$OUTPUT" \
  --conversation-id "$CONVERSATION_ID" \
  --expected-sha256 "$EXPECTED_SOURCE_SHA256" \
  --piclaw-chat-jid "$CHAT_JID" \
  --piclaw-branch-id "$BRANCH_ID"
```

Set `EXPECTED_SOURCE_SHA256` to the digest printed by `sha256sum`, not to the placeholder. For a standalone, non-Piclaw SDK copy, supply the same four core flags and omit both `--piclaw-*` flags.

The helper refuses runtime profile paths, symlinks, multiply linked inputs, sidecars, an occupied output, and input digest changes. It also refuses a target with ancestry or surviving dependants, nonterminal tasks, submissions without matching settled indexed/JSON status, unknown surviving entry/task/document kinds, and exact JSON identifier matches in surviving records. Those last checks are intentionally conservative and may reject a coincidental match. It does not search for or erase copies of text in another conversation, an artifact, an export, or a backup.

## Verification and publication

Erasure happens in a transaction on a private staging copy. `VACUUM INTO` builds the compact candidate. The helper checks SQLite integrity, that the target is gone, that survivor records are byte-equivalent at the row level, and that ID allocation metadata and the `record_ids` ledger are unchanged. It opens a separate probe copy using the public SDK in read-only mode to confirm it can reopen without starting work.

The final file is published at the new output name without replacing an existing name. A normal receipt includes the source and output digests, the output size, counts by record type, and the local SDK version used to validate and reopen the output. The 1.6.1 and 1.7.0 releases use the same SQLite layout for the standalone profile, so the receipt cannot identify which one created the input. Exit code `2` means an output was linked but directory sync or cleanup needs attention; inspect the receipt and verify the file before any reuse. Abort or refusal before publication leaves the source untouched and publishes no output. An abrupt process exit can leave a private staging directory; it is not a verified output.

**Creating `OUTPUT` is not promotion.** Keep the source and the backup, review the receipt, independently verify the compacted copy, and retain the exact backend/version compatibility evidence. Only after the Piclaw owner is stopped may an operator use the site's separate, explicit store-restore or promotion procedure to make that reviewed output active. Never point Piclaw at the output, replace its live store, or combine promotion with the reclamation command. The standalone profile refuses Piclaw tables; the two native archive flags enable only the strict, reviewed Piclaw overlay described above. The native scope does not remove arbitrary artifacts, scheduled effects, copied history, or message text copied into another conversation. The Classic delete action remains unchanged; this command is not a live button or an upstream Durable maintenance API.
