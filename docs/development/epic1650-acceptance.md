The Core migration runs on Smith at `3385b9b52f18758fc474c59655fffae52794d0ac`. The subsequent CLI, Draw.io and SQLite startup fixes are source deliveries; they have not been installed on Smith. The [17 November review and accounting](epic1650-final-review.md) keep their original source ranges and evidence.

## Supported boundary

Core is a thin product host for one public pi-durable application on SQLite. The SDK owns conversation and tool execution, task and input ordering, cancellation, results, persistence and recovery. Core owns authenticated ingress, source and workspace policy, provider credentials, event and timeline projection, and installed add-on provenance. Core does not run a resident legacy engine. The explicit offline history importer targets a fresh destination; it neither converts a live store nor schedules imported entries. Standalone `pi` is unchanged.

The approved recovery contract is forward recovery on the same store using current credentials. Preserve accepted history and uncertain outcomes. Reconcile a remote effect by its existing operation identity before considering any operator-authorised new request. An SDK task receipt cannot prove arbitrary external exactly-once execution, zero effects after cancellation, physical remote generation abort or completion of uncooperative cleanup. Unknown cleanup denies a safe restart. This contract does not cover backup restoration, returning a rotated token to service, reverse format conversion, or unnamed provider or fleet combinations.

## Cutover and forward recovery

Prepare and test the exact Core and add-on archives in a fresh disposable workspace, including non-executable assets. Record versions, archive/source hashes, host identity and database identity without copying production data or keys. Do not replace paths used by a running Core: provenance checks protect both execution and cleanup. Promotion must be coordinated with shutdown, with explicitly approved artifacts and a positive native safety check. Earlier activation approval does not grant another install or restart. If ownership or cleanup cannot be proved, stop.

When a startup fails, record the first missing or mismatched prerequisite and preserve the original failure. Qualify the correction in a fresh environment. Reconcile any uncertain operation read-only; do not retry an old activation, fabricate a terminal row or replay effects. Once the service is recovered, verify the loaded source and approved add-on set, database identity, protected state and read-only canaries. For rejected credentials, use the named grant's supported sign-in flow in its authorised profile. Never restore an older token or modify unrelated grants. A hash difference alone is not evidence that any credential is invalid.

The two incident corrections are separate: [CLI #2065](https://github.com/rcarmo/piclaw/pull/2065) reports a failed post as failure without retrying it; [SQLite #2067](https://github.com/rcarmo/piclaw/pull/2067) refuses an empty reservation before a format probe can block the exclusive creator. Zero-wait admission, nonempty-store format validation and schema ownership remain unchanged.

No new deployment, account operation, backup, restore or performance workload follows from this acceptance record.
